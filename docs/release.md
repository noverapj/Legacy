# Release Process

This repository is mirrored to GitHub, Gitea, and GitLab. All three remotes are
configured as push URLs of `origin`, so a single `git push` reaches every
platform at once.

## Versioning

- Release tags use bare semantic versioning: `MAJOR.MINOR.PATCH` (example: `1.0.0`).
- `feat:` commits bump the MINOR version.
- `fix:` and `revert:` commits bump the PATCH version.
- Breaking changes bump the MAJOR version.
- Do not use a `v` prefix.

The binary version (`0.<commit-count>.0.1`, generated by VCSGen into each
project's `Version.h`) is a build identifier derived from the git commit count.
It is unrelated to release versions and must not be edited manually.

## Creating a release

1. Make sure all intended commits are pushed to `main`.
2. Create an annotated tag:

   ```
   git tag -a X.Y.Z -m "X.Y.Z"
   ```

3. Push the tag:

   ```
   git push origin refs/tags/X.Y.Z
   ```

   The tag reaches GitHub, Gitea, and GitLab simultaneously.

4. The `Release` workflow (`.github/workflows/release.yml`) runs automatically
   and creates a release named after the tag on all three platforms. No
   manual release creation is needed.

## Release notes generation

- Notes are generated automatically from conventional commit subjects between
  the previous tag and the new tag.
- Commits are grouped under: Features, Bug Fixes, Reverts, Performance,
  Refactoring, Documentation, Miscellaneous.
- If there is no previous tag, each group is summarized instead: total commit
  count plus the latest 15 subjects.

## Required secrets

The workflow requires the following secrets configured in the GitHub
repository (Settings > Secrets and variables > Actions):

- `GITEA_TOKEN` - Gitea access token with repository write access.
- `GITLAB_TOKEN` - GitLab access token with the `api` scope.
